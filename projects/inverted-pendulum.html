Controls Lab — Design Project

Inverted Pendulum

A cart-pole system built from scratch, balanced upright by an LQR controller running at 600 Hz across two microcontrollers on a CAN bus.

The system

Rail750 mm, of which 500 mm is working travel (±250 mm about centre); the rest is safety margin
Pendulum0.31 m rod, 19.07 g PETG, 4 bearings (38.5 g) at the tip
Derived inertiaIpivot = 4.31 × 10−3 kg·m², centre of mass 25.9 cm from pivot
Sensor nodeTeensy 4.0 on the cart — reads the encoder and transmits at 600 Hz
Control nodeTeensy 4.1 off-cart — 600 Hz LQR loop
ActuationODrive S1, velocity-commanded, saturated at 1200 mm/s
Catch / drop window±0.30 rad (17°) to engage, ±0.50 rad to give up

The open-loop pendulum has an unstable pole at +5.82 rad/s — a time constant of about 172 ms. That number sets the whole design budget: whatever the controller does, it has to do it meaningfully faster than the pendulum falls.

Components

Sensor nodeTeensy 4.0 (on the cart)
Control nodeTeensy 4.1 (off-cart)
Angle encoderAS5600 — 12-bit contactless magnetic, 4096 counts/rev, read over I²C
Motor controllerODrive S1, velocity-control mode, 15 A limit during balancing
MotorElectric skateboard BLDC
Transmission24-tooth pulley, 5 mm pitch belt → 120 mm of cart travel per motor turn
Rail750 mm linear rail, belt-driven cart (~185 g)
Pendulum310 mm PETG rod (19.07 g) with 4 bearings (38.5 g) at the tip; encoder magnet at the pivot
Bus3-node CAN — SN65HVD230 transceivers, twisted pair, 120 Ω termination at each end
Interface boardsHand-soldered protoboards for both Teensy CAN interfaces
HostUSB serial for live gain tuning and telemetry

The three nodes — two microcontrollers and the motor controller — share one differential pair. The ODrive speaks CAN natively, so cart position and velocity come back over the same two wires that carry the pendulum angle.

Why distributed control

The pendulum angle has to be measured at the pivot, which rides on a cart accelerating hard in both directions. Running analogue sensor wiring the length of the rail on that cart is a good way to collect noise and eventually break a wire.

So the sensing happens where the sensor is. A Teensy 4.0 on the cart reads the AS5600 over I²C and publishes the angle on a CAN bus at 600 Hz. A Teensy 4.1 off-cart receives it, reads cart position and velocity back from the ODrive on the same bus, runs the control law, and sends a velocity command. Three nodes, one differential pair, one cable to the moving part.

Both nodes run at 600 Hz, and they match on purpose. At lower rates the angle simply was not refreshing fast enough for the loop to hold the pendulum, so the sensor rate and the control rate were raised together — there is no benefit to closing a loop faster than the measurement it depends on, and no benefit to sampling faster than the loop consumes.

CAN earns its place here: differential signalling over twisted pair, with transceivers designed for electrically hostile environments, sharing one bus between two microcontrollers and a motor controller that already speaks it natively.

Why LQR, not PID

A cart-pole has four states — cart position, cart velocity, pendulum angle, pendulum angular velocity — and exactly one input. You cannot independently command where the cart is and where the pendulum points; the only way to move the pendulum is to move the cart out from under it.

Stacking PID loops means several controllers issuing competing demands to one actuator and hand-tuning the compromise. LQR solves for a single gain vector that minimises a quadratic cost across all four states at once, so the trade-off between "keep the pendulum up" and "don't run out of rail" lives in the cost weights instead of being discovered by trial and error.

The gains that balance it

The control law is one line — a dot product of the gain vector with the state error, saturated to what the drive can deliver:

// State:  [x_mm, x_dot_mm_per_s, theta_err_rad, theta_dot_rad_per_s]
// Output: cart velocity command in mm/s
float u = -(K[0]*x + K[1]*x_dot + K[2]*th + K[3]*th_dot);

The gains that balance the rig:

K[0] — cart position−1.25
K[1] — cart velocity−2.73
K[2] — pendulum angle−6000
K[3] — angular velocity−800

The magnitudes tell the story: angle error dominates by three orders of magnitude. The controller will happily give up cart position to save the pendulum, which is exactly the right priority — you can always walk the cart back to centre once the pendulum is safe.

Those values were never compiled in. The firmware exposes k1…k4 over the serial link, so gains are editable while the pendulum is balancing. Re-flashing between attempts would have made finding four numbers slow enough that I probably wouldn't have found them.

Designing the gains, and checking the model

I wrote a design tool in Python (numpy + scipy.linalg.solve_continuous_are) that builds the linearised cart-pole from the measured hardware constants and solves the algebraic Riccati equation for a given Q and R:

# linearised cart-pole, velocity-commanded cart with loop lag tau_v
a = m_p * G * l_cm / I_pivot        # instability term        = 33.89
b = -m_p * l_cm / I_pivot           # cart-pendulum coupling  = -3.45

A = [[0, 1,          0, 0      ],
     [0, -1/TAU_V,   0, 0      ],
     [0, 0,          0, 1      ],
     [0, -b/TAU_V,   a, -d_visc]]
B = [[0], [1/TAU_V], [0], [b/TAU_V]]

P = solve_continuous_are(A, B, Q, R)
K = np.linalg.solve(R, B.T @ P)

The weak point is TAU_V, the time constant of the ODrive's inner velocity loop, which I never measured. The cart is velocity-commanded, so the pendulum only feels it through however fast that loop actually tracks — and a model resting on a guessed parameter deserves to be checked against the hardware rather than trusted.

It held up. Against the gains I converged on by hand on the rig:

tuned on the rig  ·  model  ·  error
K[0]−1.25  ·  −1.00  ·  25%
K[1]−2.73  ·  −2.39  ·  14%
K[2]−6000  ·  −4609  ·  30%
K[3]−800  ·  −801  ·  0.2%

Every gain lands within 30% of the model, and the angular-velocity gain within a fifth of a percent. For a linearisation about upright, built on a guessed actuator time constant and hand-weighed parts, that is a much better result than I expected — and it means the model is now trustworthy enough to design with: I can change a Q weight and predict which way the rig will move.

Is it critically damped? No — it is overdamped, and not marginally. Substituting the running gains into the model puts all four closed-loop poles on the real axis at −1.08, −2.54, −19.1 and −80.7 s−1. There is no complex pair, so there is no oscillatory mode to have a damping ratio at all; critical damping would need repeated poles, and these are spread across nearly two decades. Settling is governed by the slowest one — −1.08, a 0.92 s time constant — which is the cart easing back to centre long after the pendulum itself is upright. That is a deliberate trade: it buys a wide stability margin and a system that catches reliably rather than one that recovers fast and rings.

Firmware

The main controller runs a four-mode state machine:

  • IDLE — motor disarmed.
  • MANUAL — trapezoidal-trajectory moves for homing and calibration.
  • ARMED — cart holds position while the pendulum is raised by hand.
  • BALANCING — the 600 Hz LQR loop takes over, and hands back to ARMED if the angle leaves the drop window or the cart runs out of working rail.

Bringing it up follows a fixed sequence. In MANUAL I zero both x and θ with the pendulum hanging perfectly straight down, which gives the angle a known reference; then I drive the cart to 250 mm, the centre of the working rail, so it has equal room to run in either direction. Then ARM, and lift the pendulum up by hand — once it enters the catch window the controller takes it.

Angular velocity isn't measured. It's finite-differenced from successive angle readings and smoothed with a first-order low-pass filter — enough to stop encoder quantisation being amplified into the derivative term without adding so much lag that the loop destabilises.

Build

The cart, rail mounts and bearing assemblies were designed in CAD and assembled in-house; the CAN interfaces for both Teensys are hand-soldered protoboards. The rail and stand were built with my roommate, and we sourced the parts ourselves.

On tooling: I used GitHub Copilot and Claude for firmware assistance. The architecture decisions, the debugging, the LQR theory, the protocol design and the physical build were mine. AI handled boilerplate; the system-level work did not.
