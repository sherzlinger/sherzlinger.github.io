QuickCheck

A campus club platform for Cal Poly Pomona — QR join, event check-in, roster and a cash dues ledger — with every authorization decision enforced by Postgres, not by the app.

AppExpo SDK 57, React Native 0.86, React 19, Expo Router (typed file routes), iPhone only
BackendSupabase — Postgres with row-level security, SECURITY DEFINER RPCs, Realtime, Deno edge functions
AuthSupabase Auth (email/password); roles are per (user, club), not per account
Data accessOne module, src/services/db.js — screens never touch the Supabase client
Schema34 SQL migrations, applied in filename order, each one a written argument for itself
DistributionTestFlight, com.sherzlinger.quickcheck, version 2.2.0

What it is

Students find clubs, join them, and check in to meetings. Officers run the roster, post announcements, schedule events and track cash dues from the same app. A prospective member at a club fair scans a QR code that opens a hosted web page — not the custom URL scheme it originally encoded, which was broken for exactly the audience that scans it: people who don't have the app yet.

Money is a deliberate non-feature. The app records cash a treasurer says they received; there is no card, Venmo or payment-processor integration, not even as a label. A member files a payment request against a charge; an officer clears it. Nothing moves money.

Architecture

There is no server of mine in the app's request path. A screen calls a function in db.js, that function calls Supabase, and Postgres decides whether the row may be read or written. That module is also a translation layer: the app was ported from Firestore, so it maps camelCase to snake_case both ways and keeps the old function names and return shapes, which is why the screens didn't change during the port.

Two client details are load-bearing and non-obvious. The Supabase client is created with an explicit processLock; supabase-js otherwise auto-selects navigator.locks, which is broken under Hermes, and getSession() then never resolves — the app hangs on the splash screen forever. And the publishable anon key ships inside the app on purpose: every table is RLS-guarded, so what a request can reach is decided by the caller's JWT and the policies, not by the key's secrecy.

The data model, and where roles live

The interesting table is memberships: one row per (user, club) pair, carrying that pair's own role — member, treasurer or admin — plus an active/removed status and a unique constraint on (user_id, org_id). One account can be an admin of one club and a plain member of another, and every check is scoped to the club being acted on.

That table has no INSERT, UPDATE or DELETE policy at all. It is readable by the person the row belongs to and by staff of that row's club; every write goes through a trigger or a SECURITY DEFINER function. That is the backend's whole pattern — when a client needs a column it's locked out of, the answer is a narrow SECURITY DEFINER function, not a wider policy.

Authorization is in the database

Three SECURITY DEFINER helpers — has_membership(org), is_org_staff(org), is_org_admin(org) — each answer one question against memberships for the calling user. SECURITY DEFINER so a policy on another table can call them without recursing into memberships' own RLS; STABLE so the planner evaluates them once per statement rather than once per row. A member's check-in insert is then guarded by has_membership(org_id) and user_id = auth.uid() — club-scoped and self-scoped in one predicate. Events are split in two: an ALL policy on is_org_admin(org_id) for writes, a separate SELECT policy on is_org_staff(org_id), because a treasurer needs to read events for finance reports but was never shown a button to create one.

The policy I'd most want to be asked about is users_update. Its self-clause let you update your own row with no WITH CHECK, so a member could set role = 'admin' and org_id to any club. It was unreachable — but only because authenticated held no UPDATE grant on the table, and Postgres checks grants before RLS. That is not a property to depend on: the trigger mirroring users.role and users.org_id into a real memberships row is SECURITY DEFINER, and memberships is what every is_org_admin() call trusts. One GRANT — the day someone wants members to edit their own display name — and it becomes self-service admin of any club. I rewrote it while the door was still shut: a self-update must now leave role, org_id and secondary_memberships not distinct from their current values.

The bug that reshaped the schema

It surfaced on my own account: I couldn't change a member's role or remove them, and the app just said "not authorized". The root cause was one guard: auth_role() = 'admin' and auth_org_id() = (select org_id from users where id = p_user_id). Both helpers read the caller's primary club off the users row, so the check was asking "is my primary club the same as their primary club?" — a question that stopped meaning anything once membership became a per-(user, club) row. I administer that club as a secondary membership; the member I was acting on held it as their primary. I moved the RPC onto is_org_admin(p_org_id) and gave it an explicit club argument.

That fix introduced a second bug the same day. Removing someone from their primary club nulled users.org_id, and because member-level policies still keyed off that column, it cut their access to every club they still belonged to. The repair: promote a club they still have instead of clearing the field.

The third act mattered most. has_membership() had existed for a week and was called by exactly zero policies: multi-club access had been built for staff only. A plain member whose tie to a club was a secondary membership could not check in to its events, read its announcements, or submit an excuse. It was invisible in development because every account used to build the app was staff in every club, which the staff policies already covered. The fix was a set of additive permissive policies keyed on has_membership(), each mirroring the primary-club policy it shadows.

One trap runs through all of it: an RLS refusal is a silent success. A blocked DELETE returns zero rows and no error, indistinguishable from a filter that matched nothing, so a try/catch never fires. Destructive writes re-read afterwards and say so if the change didn't take.

Shipping against a backend every build shares

There is no version gate between the database and the app: a migration that tightens a policy affects the build already in a tester's pocket, immediately. That drives the migration style. New rules are added as permissive policies rather than rewrites, since Postgres OR-combines them — adding one can widen access but never break what already works. RPC overloads a shipped build still calls stay alive, because a dropped function is a crash where a refusal would have been a message. So when review found the legacy two-argument set_member_role bypassing a newer guard — the one refusing to demote a club's last admin, an unrecoverable state since every recovery path itself needs an admin — I rewrote its body to delegate to the guarded version rather than deleting it.

On tooling and review: I used Claude while building this, and had two AI reviewers sweep the backend policies and the client bundle in parallel. Every backend finding was reproduced against the live database inside an aborted transaction before I touched anything. The fixes are mine; so are the schema design, the multi-club model and the debugging.
